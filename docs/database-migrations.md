# سياسة إصدارات قاعدة البيانات

يعتمد التطبيق على MySQL/TiDB، وقاعدة Manus المُدارة مشتركة بين التطوير والاختبار والإنتاج. لذلك لا تشغّل `db:push` أو `db:migrate` من جلسة تطوير أو اختبار، ولا تستخدم قاعدة الإنتاج لاختبار migration.

## ترتيب إصدار Vercel

ينفذ `vercel-build` أولًا `pnpm build` ثم يجهّز ملفات الواجهة. لا يبدأ ترحيل الإنتاج إلا بعد نجاح البناء وتجهيز الملفات، وعندما تكون `VERCEL_ENV=production`. معاينة Vercel والبناء المحلي لا يشغّلان migration تلقائيًا. بعد نجاح migration يكمل Vercel إصدار النسخة المبنية؛ وقد يفشل التغليف/الإصدار اللاحق رغم نجاح البناء أو migration، لذلك لا تعتبر بناء الواجهة وحده دليلًا على اكتمال النشر.

اجعل migrations الجديدة إضافية ومتوافقة مع النسخة السابقة قدر الإمكان. لأن نسخًا قديمة وجديدة قد تعمل في الوقت نفسه أثناء الإصدار، استخدم أسلوب expand/contract: أضف البنية أولًا، انشر كودًا متوافقًا، وأجّل إزالة الأعمدة أو القيود إلى إصدار لاحق بعد التأكد من انتهاء استخدام النسخة القديمة.

## عند فشل migration

لا تعاود النشر أو تشغيل `pnpm db:migrate` مباشرةً إذا فشل ترحيل. أوامر DDL في MySQL/TiDB قد تثبت جزءًا من التغيير قبل فشل statement لاحق، ولا ينبغي افتراض وجود rollback ذري.

1. سجّل SHA الخاص بالإصدار واسم migration والـstatement الذي فشل، واحتفظ بسجل البناء كما هو.
2. اقرأ ملف SQL المحدد وسجل Drizzle لتحديد كل جدول أو عمود أو index أو foreign key متوقع. لا تحذف سجل migration ولا تعدّل `_journal.json` لإجبار الأداة على إعادة المحاولة.
3. افحص المخطط الفعلي للقاعدة المتأثرة باستخدام استعلامات قراءة فقط على `INFORMATION_SCHEMA`، وافحص سجل migrations الذي تستخدمه Drizzle. قارن اسم الكائن ونوعه وخصائصه الفعلية بالـDDL، لا بمجرد وجود الجدول.
4. إذا كانت الحالة غير واضحة أو اكتملت بعض statements فقط، أوقف الإصدار. يراجع مالك الإصدار حالة المخطط وسجل Drizzle ويقرر إصلاحًا forward-only محددًا قبل أي إعادة تشغيل. لا تنفذ `DROP` أو `ALTER` يدويًا ولا تضف سجلًا يدويًا من دون مراجعة واعتماد صريحين.
5. بعد حسم الحالة، أعد إصدار migration/إصلاح متوافقًا واختبره على قاعدة اختبار منفصلة إن توفرت؛ ثم أعد فحوص التطبيق ونشر الإصدار المصرح به.

Migration `0004_editable_stories` تتوقع إضافة العمود nullable `dailyStories` من النوع `JSON` إلى `program_settings`. عند أي فشل فيها، قارن تعريف العمود الفعلي وسجل migration قبل إعادة المحاولة؛ لا تفترض أن فشل الخطوة يعني أن العمود لم يُضف.
